# Оплата подписки за другого человека + подарок по стоимости

**Дата:** 2026-08-09
**Статус:** дизайн согласован, план реализации не написан

## Зачем

В поддержку регулярно приходит «как мне оплатить подписку другому человеку». Не подарить
новую, а именно продлить существующую — у друга кончился срок, а заплатить сам он не может.
Сейчас такого механизма нет: единственный способ — подарок, который покупает новый пакет по
фиксированному тарифу и ломает конфигурацию получателя.

Попутно закрывается баг: подарок обнуляет получателю лимит устройств до тарифного и стирает
все HWID-привязки, из-за чего человек с десятью устройствами остаётся с одним, а какое именно
устройство займёт слот — решает случай.

## Единый принцип

**Деньги превращаются в дни по цене получателя.**

Оплата за другого и подарок — два способа принести сумму. Сколько дней она даст, определяет
конфигурация получателя: его тариф, его допустройства, его промогруппа. Из одного принципа
следуют оба решения ниже.

Почему так: допустройства тарифицируются **за каждый период** (`pricing_engine.py:657`,
`extra_devices × device_price × months`). Значит, «месяц подписки» для человека с одним
устройством и для человека с десятью — разный товар за разные деньги. Любая схема, где
фиксированный пакет применяется к произвольному получателю, либо отдаёт лишнее даром, либо
отбирает оплаченное.

## Решения и их обоснование

| Решение | Выбор | Почему |
|---|---|---|
| Кто инициирует | Плательщик указывает получателя | Получатель без VPN не попадёт в кабинет и ссылку не создаст |
| Чем указывает | Одно поле: `@ник`, telegram id или email | @ник знают все без инструкций; `users.username` обновляется при каждом касании бота (`middlewares/auth.py:166`) |
| Что видит плательщик | Имя получателя и сумма | Тариф, срок и количество устройств — чужие данные |
| Чем платит | Баланс, если хватает; иначе любой способ | Как в остальном кабинете |
| Чья скидка | Получателя | Это его подписка; считается готовым движком цен без доработок |
| Реферальные с платежа | Никому | Это не пополнение получателя. Иначе накрутка: приглашаешь и платишь за своих |
| Нет подписки у получателя | Купить ему сразу | Отдельный поход в подарок — лишний шаг для плательщика |
| Где | Бот и кабинет | Бот доступен без VPN, кабинет удобнее |

Части A и B независимы по коду и делаются в таком порядке: сперва B (это баг, он бьёт по людям
уже сейчас и правится в одном файле), затем A.

## Часть A. Оплата за другого

### Поток

1. Плательщик открывает «Оплатить другому», вводит `@ник` / id / email.
2. Резолвер находит пользователя. Показываем карточку: имя получателя, доступные периоды с
   ценами, посчитанными по его подписке.
3. Плательщик выбирает период.
4. Хватает баланса — списываем и продлеваем в том же запросе. Не хватает — создаём запись
   «ждёт оплаты», ведём на оплату; применяем по вебхуку.
5. Получателю уходит уведомление: кто оплатил, на сколько, до какой даты.

Подтверждение получателя не требуется: деньги уже потрачены, продление ему только на пользу.

### Резолвер получателя

Новый модуль `app/services/recipient_lookup.py`:

```python
async def resolve_recipient(db, query: str) -> User | None
```

Правила разбора строки: начинается с `@` или состоит из букв/цифр/подчёркиваний → `users.username`
(без учёта регистра); только цифры → `users.telegram_id`; содержит `@` и точку → `users.email`.

Отказываем (как «не найдено», без подробностей) для: заблокированных, забаненных, удалённых,
самого плательщика (для себя показываем подсказку про обычное продление).

### Выбор подписки

Если у получателя одна подписка — берём её. Если несколько (мульти-тариф) — плательщик
выбирает из списка, где показаны только порядковый номер и дата окончания, без названий тарифов.

### Хранение

Новая таблица `sponsored_payments`, миграция `9028` (текущая голова — `9027`):

| Колонка | Тип | Назначение |
|---|---|---|
| `id` | int PK | |
| `payer_user_id` | FK users | кто платит |
| `recipient_user_id` | FK users | за кого |
| `subscription_id` | FK subscriptions, nullable | какую продлеваем; null — покупаем новую |
| `tariff_id` | FK tariffs, nullable | для случая «подписки нет» |
| `period_days` | int | |
| `amount_kopeks` | int | зафиксированная цена |
| `status` | str | `pending` / `paid` / `applied` / `failed` / `expired` |
| `payment_method`, `payment_id` | str, nullable | внешний платёж |
| `created_at`, `paid_at`, `applied_at` | timestamp | |

Индексы: по `status`, по `payer_user_id`, уникальный по `payment_id`.

**Почему отдельная таблица, а не `GuestPurchase`.** На `GuestPurchase` завязано 333 обращения в
18 файлах: лендинги, подарки, статистика продаж, слияние аккаунтов, бэкапы, мониторинг. Новый
вид записи там означал бы, что каждый потребитель обязан его отфильтровать; один пропущенный — и
оплата за друга всплывёт в отчёте по лендингам. Плюс половина колонок `GuestPurchase` (контакты
гостя, пароль кабинета, токен автологина, чеки, метки Яндекса) к этому сценарию не относится.

### Исполнение

`SubscriptionRenewalService.finalize` уже принимает пользователя и подписку разными аргументами.
Разделяем роли явно: добавляем необязательный `payer: User | None`.

- Баланс списываем у `payer` (или у `user`, если `payer` не передан — прежнее поведение).
- Промо-оффер гасим у получателя: скидка была его.
- Флаг `has_had_paid_subscription` ставим **получателю**, не плательщику. Сейчас
  `subtract_user_balance(..., mark_as_paid_subscription=True)` ставит его тому, с кого списали
  (`crud/user.py:772`). Без разделения человек, оплативший другу, сам терял бы право на триал,
  ни разу не купив себе подписку.
- Транзакция у плательщика: описание «Оплата подписки для {имя}». У получателя денежной
  транзакции нет — он ничего не тратил.

Цена фиксируется при создании записи. Если за время оплаты получатель докупил устройства и
продление подорожало — применяем по зафиксированной цене: деньги уже взяты, требовать доплату
нечестно.

При сбое применения (панель недоступна) деньги возвращаются плательщику — механика возврата в
`finalize` уже есть.

### Точки входа

Бот: пункт меню → FSM ввода получателя → карточка → выбор периода → оплата.
Кабинет: `POST /cabinet/sponsored/lookup` (резолв, отдаёт имя и цены), `POST /cabinet/sponsored/pay`.
В профиле бота у каждого показываем его «код для оплаты» (telegram id) — чтобы было что
переслать, когда ник скрыт.

## Часть B. Подарок по коду — стоимость вместо пакета

### Что меняется

Сейчас активация подарка (`guest_purchase_service.py:1424–1545`) для существующей подписки
ставит `device_limit = tariff.device_limit`, подменяет трафик и сквады тарифа, а затем
осознанно вызывает `reset_user_devices`. Комментарий в коде: «подарок = смена лимитов на
тарифные».

Становится так: **подарок добавляет дни, ничего не переключая.**

```
дни = floor(сумма_подарка / дневная_цена_получателя)
```

Дневная цена берётся из `pricing_engine.calculate_renewal_price` для подписки получателя,
делённой на длину периода. Базой берём период подарка; если у тарифа получателя такого периода
нет (`period_prices` задаёт свой набор), берём наименьший доступный — иначе движок цен откажет.
Тариф, трафик и сквады получателя не трогаем.
`reset_user_devices` при активации убирается совсем: понижать больше нечего.

Примеры при подарке за 200 ₽:

- получатель платит 200 ₽/мес → 30 дней (как и задумано);
- получатель платит 450 ₽/мес из-за десяти устройств → 13 дней;
- получатель платит 100 ₽/мес → 60 дней (мы получили 200 ₽ и отдали товара на 200 ₽).

**Остаток** от округления вниз зачисляем на баланс получателя: «зачли 13 дней, 40 ₽ на баланс».
Так ничего не испаряется и не нужно объяснять, куда делись деньги.

**Если подписки нет** — всё как сейчас: создаём по тарифу подарка на купленный период.
Конвертировать нечего, устройств нет, конфликта нет.

**Дарителю** при покупке показываем: «Получателю зачтётся сумма подарка по его тарифу — если у
него дороже, дней будет меньше». Без этой строки в поддержку придёт «я дарил месяц, а пришло 13
дней».

### Осознанное следствие

Для существующих клиентов подарок перестаёт быть «месяц такого-то тарифа» и становится «сумма,
превращённая в дни». Для новых людей всё по-старому. Это смена смысла продукта, принятая
сознательно: она закрывает обе дыры разом — и обнуление устройств, и десять устройств по цене
одного.

## Устройства

Правило: **при продлении лимит устройств не меняется.**

- Оплата за другого устройств не касается: обычное продление `device_limit` не трогает
  (проверено — `subscription_renewal_service.py` передаёт в `extend_subscription` тариф, трафик
  и сквады, но не лимит устройств).
- Подарок больше не подменяет лимит и не сбрасывает HWID.
- Новая подписка создаётся с тарифным лимитом — устройств у неё ещё нет.

## Приватность и злоупотребления

- Резолвер под рейт-лимитом (10 попыток в минуту на пользователя, как на активации подарка,
  `cabinet/routes/gift.py:740`) — иначе ники и id можно перебирать, выясняя, кто наш клиент.
- В карточке только имя и сумма.
- Заблокированным, забаненным и удалённым платить нельзя; ответ неотличим от «не найдено».
- Один платёж применяется ровно один раз: повтор вебхука не удваивает дни.

Ограничения на количество получателей у одного плательщика **не вводим**: перепродажа для
VPN-бизнеса скорее плюс. В логах это видно, вернёмся, если начнёт мешать.

## Уведомления

- Получателю: «Вашу подписку оплатил {имя} — {N} дней, теперь до {дата}».
- Плательщику: подтверждение с суммой и именем получателя.
- Даритель подарка узнаёт, что подарок активирован, — как сейчас.

## Тестирование

- Резолвер: каждый формат ввода, регистр ника, заблокированные и удалённые, сам себе.
- Разделение ролей в `finalize`: списано у плательщика, продлена подписка получателя, флаг
  `has_had_paid_subscription` у получателя, промо-оффер погашен у получателя.
- Реферальные с платежа не начисляются никому.
- Фиксация цены: подорожание между созданием и оплатой не меняет сумму.
- Идемпотентность: повторный вебхук не добавляет дни второй раз.
- Возврат плательщику при сбое применения.
- Конвертация подарка: три примера выше, округление вниз, остаток на баланс.
- Подарок не меняет `device_limit` и не вызывает `reset_user_devices`.
- Подарок человеку без подписки создаёт её по тарифу подарка (прежнее поведение не сломано).

## Вне рамок

- Возврат из fallback-сквада: три пути (`crud/subscription.py:1506`,
  `admin_expiry_fallback.py:131`, `remnawave_webhook_service.py:1316`) шлют в панель
  `pre_expiry_expire_at` — дату в прошлом, которую RemnaWave 3.2.0 отвергает
  (`Expiration date cannot be in the past`). Дефект настоящий, но к этой работе не относится:
  чинится отдельно.
- Ограничение числа получателей, реферальные за оплату другому, подарок с выбором «дни против
  устройств» — сознательно не делаем.
