# Резервный метод входа при оплате — дизайн (фича B)

**Дата:** 2026-07-31
**Статус:** дизайн утверждён владельцем, готов к плану
**Репозитории:** `remnawave-bedolaga-telegram-bot` (backend `app/`) + `bedolaga-cabinet` (frontend `src/`)

## Проблема / цель
У пользователя часто **один способ входа** (только Telegram, либо только email). Главная цель — **удобство возврата и продления**: когда подписка кончится, пользователь должен легко **зайти на сайт (кабинет) и продлить** в любой момент. Для этого у него должен быть веб-вход (email/пароль или OAuth Яндекс). Вторичный, но тоже важный плюс — **не потерять аккаунт**, если сменит Telegram/номер. Поэтому в момент оплаты подписки **мягко предлагаем привязать резервный метод входа**. Резервным может быть любой наш метод: **Telegram, email/пароль, Яндекс** (и другие настроенные OAuth).

Посыл — **позитивный** («привяжи вход по почте/Яндексу — заходи на сайт и продлевай подписку в любой момент»), а не пугающий.

## Решения (утверждены владельцем)
- Показывать **и в боте, и в кабинете**.
- **Мягкое** предложение (закрываемое, покупку не блокирует).
- Триггер — **после успешной оплаты подписки** (покупка/продление). Не на пополнение баланса.
- Показывать только если у юзера **≤ 1 метода входа**; при **каждой** такой оплате, пока метод один. Стало ≥ 2 — больше не показываем.
- Не выбираем конкретный «недостающий» метод — ведём в существующий экран привязки (`ConnectedAccounts`), где доступны все методы (email, Яндекс, Telegram и т.д.); юзер выбирает сам.

## Что уже есть
- `compute_auth_methods(user)` / `_count_auth_methods(user)` (`app/cabinet/routes/account_linking.py:223`) — число методов входа.
- Привязка: кабинет `src/pages/ConnectedAccounts.tsx` (email + OAuth Яндекс/Google/… + Telegram), бот `account_linking.py` (link-email/link-telegram). Переиспользуем — новую логику привязки НЕ пишем.
- Флоу оплаты: бот `app/services/subscription_purchase_service.py` / `app/handlers/subscription/tariff_purchase.py` / `purchase.py`; кабинет — экран успешной оплаты подписки.

## Архитектура

### Backend (бот, `app/`)
1. **Хелпер** `needs_backup_login(user) -> bool` (напр. в `account_linking`-services или отдельном модуле) = `_count_auth_methods(user) <= 1`. Единая точка правды.
2. **Эндпоинт кабинета** `GET /cabinet/backup-login-suggestion` (под текущим cabinet-auth) → `{ needs_backup: bool }`. Читает `needs_backup_login(current_user)`.
3. **Бот — доп-сообщение после оплаты подписки.** В точке(ах), где бот шлёт сообщение об успешной покупке/продлении подписки, ПОСЛЕ него: если `needs_backup_login(user)` — отправить отдельное сообщение (позитивный посыл): «🔐 Привяжи вход по почте или Яндексу — сможешь заходить на сайт и продлевать подписку в любой момент (и не потеряешь аккаунт при смене Telegram).» с кнопкой **«Привязать вход на сайте»** → URL-кнопка, открывающая кабинет на разделе привязок (ConnectedAccounts). Best-effort: сбой отправки не влияет на покупку. Не отправлять, если методов ≥ 2.

### Frontend (кабинет, `src/`)
4. **API** `getBackupLoginSuggestion()` → `{ needs_backup }`.
5. **Плашка/модалка после оплаты подписки.** На экране успешной оплаты подписки (там, где кабинет показывает результат покупки/продления), если `needs_backup` — закрываемая плашка (позитивный посыл): «Привяжи резервный способ входа (почта или Яндекс) — сможешь заходить на сайт и продлевать подписку в любой момент» + кнопка **«Привязать»** (→ переход на `ConnectedAccounts`) + **«Позже»**. Не блокирует. Показывается при каждой оплате, пока методов < 2 (после привязки второго — эндпоинт вернёт `needs_backup=false`).
6. **ConnectedAccounts** — без изменений (уже умеет привязывать email/Яндекс/Telegram/…); плашка просто ведёт туда.

## Обработка ошибок / крайние случаи
- Бот: отправка доп-сообщения обёрнута в try/except — сбой не ломает покупку.
- Кабинет: сбой `getBackupLoginSuggestion` → плашку не показываем (не мешаем).
- Гость/незалогиненный — эндпоинт под auth; для гостевых покупок плашка не применяется (нет current_user).
- Юзер с ≥ 2 методами — `needs_backup=false`, ничего не показываем.
- URL-кнопка бота ведёт на страницу привязок кабинета (ConnectedAccounts); авто-логин не обязателен (юзер логинится в кабинете обычным образом) — если авто-логин уже есть в проекте, можно переиспользовать, но это НЕ требование.

## Тестирование
- **Backend unit:** `needs_backup_login` — 1 метод → True, 2 метода → False. `GET /backup-login-suggestion` — форма ответа + auth-гейт. Бот: после оплаты подписки single-method юзеру доп-сообщение отправляется; ≥ 2 методов — не отправляется; сбой отправки не роняет покупку (мок bot.send_message).
- **Frontend:** сборка `tsc`+`build`+`vitest`; плашка показывается при `needs_backup=true` и ведёт в ConnectedAccounts; при `false` — не показывается; «Позже» закрывает.

## Вне объёма
- Новая логика привязки методов (используем существующую ConnectedAccounts / bot link-*).
- Принудительная (блокирующая) привязка — только мягкое предложение.
- Триггер на пополнение баланса (только оплата подписки).
- Авто-логин из бот-кнопки в кабинет (опционально, если уже реализован; не требование).
