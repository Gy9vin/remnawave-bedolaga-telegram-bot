# Патчноут — черновик, накапливается по ходу работ

Статус: **черновик**. Дописывается по мере закрытия волн. Итоговая версия
собирается в конце и заменяет этот файл.

---

## 1. Безлимит устройств больше не превращается в «1»

**Коммиты:** бот `1c0ce1fb`, кабинет `6cab764`

**Что было.** У пользователя с отключённым лимитом HWID кабинет показывал
«41 устройство из 1 доступного».

**Причина.** `device_limit == 0` означает «лимит HWID отключён» — так это
понимает и панель RemnaWave (`subscription.service.ts`, ветка
`user.hwidDeviceLimit === 0` возвращает `limitBypassed: true`). Часть кода бота
это уже учитывала, но слой отправки в панель считал ноль невалидным и не
отправлял его вовсе, а идиома `device_limit or 1` подменяла безлимит единицей
при докупке устройств, переключении модема и в админских списках. В итоге бот
физически не мог выразить безлимит.

**Что изменилось.** Ноль доезжает до панели как безлимит; отсекаются только
`None` и отрицательные значения. Принудительный лимит режима больше не
схлопывает выданный безлимит. Докупка мест и уменьшение лимита при безлимите
отказывают осмысленно. В кабинете везде показывается «∞».

**Действия при выкате:** никаких настроек не требуется.

**Внимание.** У тех, кто уже расcинхронизировался, в базе бота лежит неверное
значение. Проверить и поправить:

```sql
-- посмотреть подписки, где бот думает «1», а в панели стоит безлимит
SELECT s.id, s.user_id, s.device_limit
FROM subscriptions s
WHERE s.status = 'active';
-- сверить с панелью и выставить 0 там, где в панели hwidDeviceLimit = 0
```

## 2. Оплата больше не оставляет человека в fallback-скваде

**Коммит:** бот `9c8c01fa`

**Что было.** Пользователь оплачивал подписку и оставался в fallback-скваде:
доступа нет, приходилось вручную менять сквады в панели. У одних не срабатывало
никогда, у других работало всегда.

**Причина, три звена.** Сквады уезжали в панель через условие
`if subscription.connected_squads:` — пустой список в Python ложен, поэтому при
пустом `connected_squads` поле `active_internal_squads` не попадало в запрос, а
частичный PATCH оставлял панель как была. Следом безусловно снимались
fallback-флаги в базе, хотя панель никто не тронул. После снятия флагов подписка
становилась невидимой и для периодического reconcile, и для скрипта
`repair_stuck_fallback.py` — оба отбирают строки по этим же флагам.

**Что изменилось.** На путях покупки и продления вызывается настоящее
восстановление сквадов с проверкой результата; флаги снимаются только после
подтверждения. Гейт отправки больше не молчит при пустом `connected_squads` у
fallback-подписки. В reconcile добавлена страховочная сеть, которая находит и
чинит уже застрявших.

**Действия при выкате:** никаких настроек не требуется. После выката первый же
прогон reconcile (интервал `EXPIRY_FALLBACK_RECONCILE_INTERVAL_MINUTES`, по
умолчанию 15 минут) подхватит застрявших.

**Проверить, сколько людей это затронуло:**

```sql
SELECT count(*) FROM subscriptions
WHERE status = 'active'
  AND expiry_fallback_active = false AND traffic_fallback_active = false
  AND (connected_squads IS NULL OR connected_squads::text IN ('[]', 'null'));
```

## 3. Простой режим кабинета, волна 1: каркас

**Коммиты:** бот `187fb436`, `f128669e`, `42a5c610`;
кабинет `459443e`, `50eb72c`, `d8657d0`, `1d119ca`, `e0cd797`

**Что появилось.** В Профиле переключатель «Простой интерфейс». Включённый режим
сворачивает меню с 8 пунктов на десктопе и 11 в мобильном гамбургере до четырёх:
Главная, Подписка, Рефералы, Профиль. Выбор хранится в базе и переживает смену
устройства.

**Миграция:** `9029_user_cabinet_ui_mode` — добавляет колонку
`users.cabinet_ui_mode` (`String(16)`, nullable, без бэкфилла). Применяется
автоматически при старте.

**Существующие пользователи изменений не увидят:** у всех значение `NULL`,
глобальный флаг выключен, эффективный режим — полный кабинет.

### Настройки

**`CABINET_LITE_MODE_ENABLED`** — глобальный дефолт интерфейса. Это **не
переменная окружения**, а системная настройка в базе. Читается и пишется через
эндпоинты `GET`/`PATCH /cabinet/branding/lite-mode`. Значение `'true'` означает,
что все, кто сам ничего не выбирал, получают простой режим.

Переключателя в админке кабинета пока нет — это долг следующей волны. Пока
включать так:

```bash
# посмотреть текущее значение
docker exec remnawave_bot python3 -c "
import asyncio
from app.database.database import get_db
from app.database.crud.system_setting import get_setting_value

async def main():
    async for db in get_db():
        print(await get_setting_value(db, 'CABINET_LITE_MODE_ENABLED'))
        break

asyncio.run(main())
"
```

### Порядок раскатки

1. Выкатить как есть. Глобальный флаг выключен, никто изменений не замечает.
2. Себе в Профиле включить «Простой интерфейс» — увидите только вы.
3. Проверить вживую, поправить замечания.
4. Включить `CABINET_LITE_MODE_ENABLED` — простой режим станет дефолтом для
   тех, кто сам не выбирал. У нажавших «выключить» записан явный выбор, их это
   не заденет.
5. Откат — тем же флагом.

### Проверить перед выкатом

Юнит-тесты зовут обработчики напрямую, минуя сериализацию FastAPI. Один раз
дёрнуть руками:

```bash
curl -s -H "Authorization: Bearer <токен>" https://<кабинет>/api/cabinet/info/user/ui-mode
curl -s -X PATCH -H "Authorization: Bearer <токен>" -H 'Content-Type: application/json' \
  -d '{"mode":"simple"}' https://<кабинет>/api/cabinet/info/user/ui-mode
```

## 4. Простой режим кабинета, волна 2: доработки в боте

**Коммиты:** `d839d491`, `50e75462`, `4752aec8`, `c3be677a`, `bf927ed3`, `069dc76d`, `5f906018`

Четыре изменения в API, которые нужны экранам следующей волны. Миграций нет,
переменных окружения не требуется.

### Название клиентского приложения в списке устройств

`GET /cabinet/subscription/devices` теперь отдаёт у каждого устройства поле
`client` — «Happ», «INCY» и так далее.

Почему это важно: hwid выдаётся на **установку приложения**, а не на телефон.
Две программы на одном телефоне занимают два места. Без названия клиента человек
видит список, где устройств больше, чем у него есть, и идёт в поддержку. Панель
хранила это поле всё время, кабинет его просто не читал.

Неразборчивый user-agent даёт `null`, а не строку «Unknown» — фронт в этом случае
показывает платформу и модель.

### Выборочное отключение нескольких устройств

Новый эндпоинт `POST /cabinet/subscription/devices/delete-batch`, тело
`{"hwids": [...]}`, максимум 50 штук за раз.

Раньше было только удаление по одному и «снести все». Отказ по одному устройству
не останавливает остальные и **не выдаётся за успех**: ответ содержит
`deleted_count` и `failed_hwids`, а `success` равен `false`, если хоть одно не
отключилось.

### Уменьшение лимита устройств: выбор и возврат денег

`POST /cabinet/subscription/devices/reduce` принимает новое **необязательное**
поле `hwids_to_remove`. Старые клиенты, которые его не шлют, продолжают работать.

Два исправления сразу:

**Возврат денег.** Раньше уменьшение лимита не возвращало ничего, хотя покупка
места пропорциональна оставшимся дням. Теперь возврат считается зеркальной
формулой — цена места на оставшийся срок, с той же скидкой промогруппы, что и при
покупке, — и начисляется на баланс с типом «возврат», то есть **попадает в историю
операций**. Сумма видна до нажатия в ответе `GET /devices/reduction-info`, поле
`refund_kopeks_per_slot`.

Возврат считается от **текущей** цены места, а не от уплаченного: истории покупок
устройств в базе нет. Практическое следствие — если вы измените цену устройства,
человек, купивший место по старой цене, получит возврат по новой.

**Выбор отключаемых.** Раньше система выбирала жертв сама и из-за среза с конца
отсортированного по активности списка удаляла **самые свежие** устройства — то,
чем человек только что пользовался. Теперь список приходит от него, а неверное
количество или неизвестный hwid дают отказ до похода в панель и до начисления
денег.

Важное правило, которое видно в интерфейсе: **количество отключаемых устройств и
количество освобождаемых мест — разные величины**. Мест освобождается «старый
лимит минус новый». Устройств отключать надо «сколько подключено минус новый
лимит», и это число бывает нулём.

### Готовые суммы пополнения

Новый эндпоинт `GET /cabinet/balance/topup-presets`. Отдаёт до четырёх сумм,
равных ценам действующих периодов: в тарифном режиме из тарифов, доступных этому
пользователю с учётом его промогруппы, в классическом — из настроек `PRICE_*_DAYS`.

Смысл: пополнил ровно на тариф и купил без остатка на балансе. Одинаковые цены
схлопываются в одну кнопку.

### Действия при выкате

Настроек не требуется. Проверить руками после выката:

```bash
curl -s -H "Authorization: Bearer <токен>" \
  https://<кабинет>/api/cabinet/subscription/devices | jq '.devices[0]'
curl -s -H "Authorization: Bearer <токен>" \
  https://<кабинет>/api/cabinet/balance/topup-presets
```

## Настройка, которую надо не забыть

`AUTO_PURCHASE_AFTER_TOPUP_ENABLED` по умолчанию **выключен**
(`app/config.py:697`). Простой режим обещает человеку «подписка включится сама
после пополнения» — и это обещание держится ровно на этом флаге. Пока он выключен,
экраны будут врать.

Флаг зарегистрирован в системных настройках (категория PAYMENT), то есть меняется
из админки, либо переменной окружения `AUTO_PURCHASE_AFTER_TOPUP_ENABLED=true`.

Включать нужно **до** выката экранов третьей волны, не раньше и не позже.
